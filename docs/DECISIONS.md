# Decisions

A running log of choices and why. Newest at the bottom. Append; do not rewrite.

## 2026-09-10 — Build a test app to learn three concepts
Ben wants hands-on understanding of governance/guardrails, orchestration/agentic chains, and context engineering/RAG, via something that becomes usable. Two projects in parallel to accelerate learning; this is one of them.

## 2026-09-12 — Provider PA tool → patient navigator
Started as a provider-side "what does the payer require" tool. Rejected because that space is crowded (CoverMyMeds, Develop Health, others) and payers are being pushed to expose requirements directly. A patient-facing tool that starts from the patient's plan and shows step therapy, documentation, timelines, and appeals is a gap nobody serves.

## 2026-09-12 — Add the second layer: routes around coverage
Patients' real options span the plan's policy, manufacturer programs (DTC pharmacies, copay cards, assistance), and discount-card cash for generics. Nobody presents these together at the class level; brand DTC sites are single-brand and price sites don't start from the plan. Two layers on one screen: "what your plan says" and "your best long-term route."

## 2026-09-12 — Migraine first, not MS
Higher volume, more formulaic step therapy, patients more likely to self-navigate, and real manufacturer DTC presence (LillyDirect for Emgality, PfizerForAll for Nurtec/Zavzpret). MS becomes the second category on the same engine.

## 2026-09-12 — Correction on CMS-0057-F
The 2027 Prior Authorization API mandate covers medical-benefit items and services for CMS-regulated payers; drugs are carved out and pharmacy PA stays on NCPDP ePA. Relevance to a mostly-pharmacy-benefit migraine tool is limited. The Patient Access API (live since 2021 for those payers, includes pharmacy claims) is the useful one, and is a V2 feature because it involves PHI.

## 2026-09-12 — No patient data in V1
V1 answers from public policy and program documents plus a plan match. No claims, no clinical detail, no storage. This keeps V1 outside HIPAA-covered territory and makes the guardrails testable. Card images are processed in memory and discarded.

## 2026-09-12 — Name: Trailhead Rx
Chosen over descriptive options (CoverageNav, InsuriNav) and other metaphors (Rungs, Covered Compass) because it fits the "routes" language of the results screen and stretches beyond insurance. trailheadrx.com was unregistered at RDAP check on 2026-09-12; trademark check pending.

## 2026-09-12 — Public repo, corpus stays out
Repo is public for portfolio purposes. Payer documents carry terms of use, so only manifests (source URLs, versions, dates) are committed; documents are downloaded locally. Enforced by `.gitignore`.

## 2026-09-12 — Architecture framed as three layers outside the LLM
Ben's earlier "LLM stack" framing: (1) context engineering / memory / RAG, (2) model orchestration and agentic chains, (3) cognitive governance and guardrails. Trailhead Rx maps onto it as before / around / wrap: context engineering shapes the packet the model sees, orchestration sequences the calls, governance gates inputs and outputs and keeps the record. See docs/ARCHITECTURE.md. Rendered view: https://claude.ai/code/artifact/f06efd1a-47d8-4c2e-b9ac-0e18452c91af

## 2026-09-12 — Architecture relabeled in industry vocabulary; FLUENCY.md added
Ben's goal is fluency in how modern applications use LLMs: what happens inside the model versus before, around, and after it. The diagram now shows the model's five internal steps (tokenizer → embeddings → transformer blocks → logits → sampling) as the untouchable core, and labels every outside component with its industry term (ingestion, chunking, embeddings, vector store, hybrid retrieval, prompt assembly, routing, chain, fan-out, LLM-as-judge, input/output guardrails, rules-as-code, tracing, evals). docs/FLUENCY.md maps each term to our component and gives the "how to say it" sentences.

## 2026-09-12 — Session 2: Layer 1 vertical slice
Built ingest → hybrid retrieval → router → prompt builder → verifier → output guardrails → audit, a CLI, 14 tests, 17 eval scenarios. Choices: local embeddings (all-MiniLM) plus SQLite FTS5 so the only API key is Anthropic's; no orchestration framework, plain Python on the SDK, so every step is visible; structured output (claims with passage numbers) so citations are checkable by code before any judge model runs; dry-run mode when no key is present so tests and most evals run for free. ## 2026-09-13 — First live run: verifier tuned, revise loop replaced with prune
First live request (UHC commercial, Emgality) drafted an accurate plain-language answer three times and abstained three times: each attempt failed one claim on the code-level word-overlap check (scores 0.20–0.23 vs a 0.25 threshold) before the judge model ever ran, and each redraft introduced a new borderline claim, so the loop never converged. Two changes: (1) the overlap check is now a backstop that fails only near-zero overlap (0.08); paraphrase support is the judge's call, which is what LLM-as-judge is for; (2) when a minority of claims fail and at least two pass, the pipeline prunes the failed claims and ships the rest with a warning, instead of regenerating. Redraft is reserved for broken JSON or majority failure. Lesson: rules G2 (cite everything) and G7 (plain language) pull against each other, and a verifier must be designed for paraphrase, not string matching.

## 2026-09-13 — Product stance: the patient's coverage advocate
The first live trace showed UnitedHealthcare's CGRP policy waives the non-CGRP step therapy for California members and shortens the trial to 30 days in Connecticut, Kentucky, and Mississippi, while an Ohio member must fail two preventives for two months each. Ben's call: Trailhead Rx is the patient's coverage advocate, and this is exactly the information it should surface — not only "what your plan requires of you" but "what the same plan requires of someone in another state, and why that difference exists" (state mandates, not clinical judgment). Transparency that payers would rather not offer is the product. Consequences: plan match needs the member's state, not just the payer; the answer schema gets a `variation` topic so state and plan-type differences are first-class claims with citations; the Ohio step-therapy exemption law is presented as a lever, not a footnote; and the doctor summary should tell the prescriber which exception arguments the policy itself supports.

## 2026-09-13 — Plainspeak output, wait estimate, class comparison, and three lessons from live runs
Output is now written and laid out for a patient: everyday headings, "the short version" first with a months-from-zero wait estimate, "what we left out and why" showing unconfirmed statements instead of a warning count, and a "how to use this" section stating the advocacy stance. First "other ways to get it" pointer (manufacturer direct purchase) until session 3 verifies program terms. `--compare-class` fans out one retrieval + extraction per medicine in the class and renders a coverage-path table (paperwork and waiting only, never effectiveness — G1).
Three lessons from the first live runs, each now handled in code:
1. The output token budget is a governance setting. Drafts cut off at the limit arrive as broken JSON and look like a model fault. Budget raised to 16k; stop_reason recorded in the trace; a cutoff retries shorter.
2. The verifier must be built for paraphrase. A word-overlap check failed accurate plain-language claims; it is now a near-zero backstop, the judge decides support, and failed claims are pruned rather than the whole answer redrafted (pruning converges; regeneration does not).
3. Fan-out over shared documents produces wrong-drug attribution. The Aimovig row inherited Ajovy's "fail Aimovig and Emgality first" rule because both drugs share the same passages. Every comparison row is now judged for "is this requirement stated for THIS medicine," and WRONG_DRUG rows are withheld with a plain explanation.

## 2026-09-13 — Session 3: verified programs corpus, Ohio appeal law as citable passages, scoring explainer
Layer 2 is now data plus rules, not the model. `corpus/programs/manifest.yaml` holds one record per medicine (direct purchase, copay card, bridge fill, patient assistance) with the maker's URL and the date each was read; `programs.py` renders "other ways to get it" in the order a patient would use them (bridge → card → skip the plan → assistance) and applies rules-as-code, so a Medicare or Medicaid member sees the card marked unavailable with the reason rather than a dead link. "not_found" is written where a page did not state a figure, and a `confidence: low` flag (Aimovig's $5 vs $49 conflict, Lundbeck's PAP) is rendered as "call to confirm." Freshness: 45 days for program records versus the policy-document threshold, because program terms change monthly. Reyvow is marked discontinued and rendered as such.
Appeal questions now retrieve citable law. The Ohio Department of Insurance's external-review page is a landing page (toolkit links, no rules) and refused non-browser fetches, so it stays `landing_only`; the citable rules come from ORC 3901.832 (step-therapy exemption) and ORC 3922.02/.08/.09 (external review: 180-day window, five-day file deadline, expedited path). These are `line_of_business: reference` rows: `build_packet` adds them to the retrieval set only when the question mentions appeal/denial/exception and the plan is state-regulated (Medicare Advantage appeals run through CMS), and they never affect plan-match confidence. `data/drugs_migraine.yaml` now points at the programs manifest instead of carrying placeholders.
`docs/concepts/weighting-and-scoring.md` explains, with worked numbers from the first UHC run, where every score in the pipeline comes from (BM25, cosine, RRF, the lexical floor, the judge) and which knob does what. Tests: 17.

## 2026-09-13 — Session 4: the website, and governance at the edge
The form is FastAPI with plain HTML templates and no JavaScript, so every file stays readable and there is nothing to build. It runs the same `pipeline.answer()` the CLI runs; the web layer adds only what a shared link needs. Three gates sit in front of the pipeline and each is tested: a shared access code (typed once, kept as a signed cookie that never contains the code; wrong tries are counted and slowed, never logged), a per-visitor rate limit, and a daily spend cap of $5 computed from the cost estimates the audit trace already records plus a reservation for jobs in flight. Input guardrails run before a question is queued, so a refused question never occupies a worker. Answers run in a two-thread background pool and the page refreshes itself until one is ready; finished answers live in memory for an hour and are then dropped.
Ben's calls: include a collapsed "How this answer was built" panel on every answer (plan match, retrieved passages with keyword/semantic/fused ranks, per-claim verifier verdicts, model calls and cost) — patients see the plain answer, testers can see the machinery; and cap spend at $5/day. The form offers only payers and medicines we hold records for (discontinued Reyvow and the law references are excluded), which closes off the most common route to an "I don't have that document" answer before it is asked.
The web tests caught a PHI gap on the first run: "my member id is AB12345678" passed the ID pattern because it only allowed ":" or "#" after the label. The pattern now accepts "is", "=", ":", "#", or nothing, plus a second pattern for "my member/subscriber/policy number … 1234…". Tests: 24.

## 2026-09-13 — First user test of the website: form, abstain wording, self-funded plans
Ben's first pass on the site produced five changes. (1) The form now leads with a menu of the questions the pipeline answers well (try first, what the doctor must show, how long, appeal, cost and other routes) with free text as an optional addition, so a visitor is steered toward answerable questions instead of discovering the limits by trial. (2) Labels are larger and inputs shaded; copy reworded to his wording ("Learn what my plan's rules dictate"; "Include all the medicines in this class, comparing timing and cost of each path"). (3) The health-plan menu lists only payers with an indexed document, and abstain reasons are written for a patient ("we know where the rules are but have not loaded them yet — check back") rather than for the developer. (4) Every result page ends with action buttons. (5) Self-funded employer plans: the claim that they fall under federal rather than Ohio law is correct — ERISA preempts state insurance mandates, so ORC 3901.832 does not apply — but "federal rules" was an empty phrase until now. Two federal references are added to the corpus (29 CFR 2560.503-1, the ERISA claims procedure with its 15-day/72-hour decision and 30-day appeal clocks; 45 CFR 147.136, the ACA internal-appeal and external-review rules that reach self-funded plans) and retrieval routes appeal questions to them when the member says the plan is self-funded, to Ohio law otherwise. Ben's point stands: most commercial members are in self-funded plans, so the federal path is the common case, not the edge case. Tests: 26.

## 2026-09-14 — Judge calibration: PARTIAL keeps the claim
First live Aetna answer dropped its most useful statement — the list of ten preventives, any of which for 56 days satisfies step therapy — because the judge returned PARTIAL with the reason that "in the last 2 years" is less precise than "within the past 730 days," and PARTIAL was treated as a failure. That is a paraphrase, which rule G7 requires, not an error. Two changes: the judge prompt now says plain-language paraphrase, unit conversion, rounding, and describing a rule's effect rather than its mechanism all count as SUPPORTED, and PARTIAL is reserved for a claim that adds a detail the passage lacks; and in code only NOT_SUPPORTED (and WRONG_DRUG in the class comparison) drops a claim — a PARTIAL claim ships, with the judge's reservation recorded in the trace and shown in the "How this answer was built" panel. `trailheadrx trace` now prints the judge's reason for any non-SUPPORTED verdict. Lesson four for the list in FLUENCY: a judge needs a calibrated rubric as much as a verifier needs a paraphrase-tolerant check; "strict reviewer" produced strictness about the wrong thing.

## 2026-09-20 — fix27: lead time is arithmetic, so it is done in code; grid cells expand in place
Ben's live Aetna run showed Emgality at "2–3 months" in the lead-time box and "4 months" in the grid, Ajovy at 3, Aimovig "not stated" — from the same policy. Both numbers were the model's arithmetic: the answer's `wait_estimate` by the strong model, the grid's `months_estimate` by the small one, each told to "add the trial lengths plus half a month". Two models, two sums, and the small one had folded in the cluster-headache rule and the 3-month continuation requirement, which are not part of a new patient's path. The fix moves the sum out of the model: the extractor now returns `steps` — one entry per required try for the first approval, with the stated length in days, excluding continuation, renewal, other-diagnosis and combination rules — and `compare.months_from_steps()` turns that into months (sum of days, plus two weeks for the plan's review, rounded to a range: 56 days → 2–3, two 56-day tries → 4–5, 90 days → 3–4). The same rule for every medicine, testable, and printable in the cell ("one other preventive (56 days), plus about two weeks for the plan's review"). The lead-time box uses this number whenever the comparison ran, and the model's own estimate only when it did not. Rule of thumb recorded in LESSONS.md: if a number is a sum, the model names the parts and code adds them.

Grid cells: the long "must try first" text (Aetna's list of every oral preventive) made row A unreadable. Each cell now shows a one-line summary the extractor writes (`must_try_first_short`, at most 8 words) and a "What it takes" toggle that opens the full requirement, the step-by-step lead time, and any note — inside that cell only, no JavaScript, the same `<details>` mechanism as the page's other expanders. A hover tooltip was considered and rejected: no hover on a phone. Row B's description moved to the Path column since it was the same in every cell. The path letters are drawn the same way in the grid as on the card (the block-display override that squashed them is gone).

## 2026-09-20 — fix29: "What if I had a different plan?" and finding out what your employer actually does
A second comparison, loaded from a button at the bottom of the answer like the class comparison: the same medicine under every other held plan of the same kind (for commercial today: Aetna, Aetna/CVS criteria, CVS Caremark, Anthem/CarelonRx, Cigna/Express Scripts, Express Scripts, UnitedHealthcare/Optum Rx, Medical Mutual). Cached and rate-limited like the rest; about six to eight small-model calls. The two option forms at the bottom are now just a checkbox, the label and a Load button ("Compare comparable medications" / "What if I had a different plan?"); each disappears once its comparison is on the page.

Ben's harder question — can we tell whether a given employer applies step therapy? — has no automatic answer from public data: the carrier's published policy is the standard rulebook, and a self-funded employer can adopt, loosen, tighten, exclude, or hand the medicine to an alternative funding program without publishing any of it; the plan's real flags sit behind the member login. So the page tells the reader how to find out, in a card shown for commercial plans: the plan's own drug lookup (PA/ST/NC flags), the SPD and drug rider HR must provide under ERISA, one question to ask HR ("self-funded? carrier's standard criteria or our own?"), and the employer's Form 5500 at efast.dol.gov as a public self-funded check (with the DOL's own caveat that the filing is not always clear and small employers do not file). It closes with the alternative-funding warning: a "not covered" plus a referral to an outside company to apply for the maker's assistance is an AFP, several makers now refuse those applications, and a written denial is what unlocks an exception request and an appeal. Sources are linked and dated on the card; content is static template text, not model output, so it is reviewable in one place.

## 2026-09-20 — fix31: dropped connections to the model are retried, and a failed answer can be re-run in place
Ben hit "APITimeoutError: Request timed out or interrupted" on a live run. The strong-model draft has a 16,000-token budget and can run for minutes on one open connection; the client was using the SDK defaults (a plain, non-streaming call). Three changes. The client now streams every call (the SDK's own recommendation for long requests — the connection carries data the whole time instead of sitting idle until the reply is complete), with a 15-minute per-attempt timeout and three SDK-level retries with backoff; on top of that the job runner retries the whole answer once more after a timeout or connection error, since a passing network fault should not cost the visitor their answer. The failure page no longer shows a stack-trace string for these cases; it says the connection dropped, that nothing was stored, and offers "Try the same question again" (a `POST /a/<id>/retry` that resubmits the same request, rate-limited like everything else) beside "Start over". Other errors still show their text, because those are the ones Ben needs to see.

## 2026-09-20 — fix33: every path is always drawn; the ones your plan rules out are greyed with the reason
Reverses part of fix26. There, a path that applied to nobody on the page (usually D on a commercial plan) was dropped and replaced by a note. ## 2026-09-20 — session 5, part 1: the Fly.io image, hardening for HTTPS, and the deploy runbook
Hosting is Fly.io (chosen earlier: secure, cheap, a single machine near Ohio). The image carries everything an answer needs — code, corpus documents, the built index, the embedding model — so a machine starts ready and never fetches at request time; corpus documents stay out of the public repo (.gitignore) but go into the private image (.dockerignore now allows them). The index is built during the image build, with no API key. Secrets (API key, access code, cookie signing secret) are Fly secrets; what the app writes (audit trace, plan-name requests) goes to a 1 GB volume at /data via the existing TRAILHEADRX_* path overrides. The machine is shared-cpu-1x with 2 GB (torch + MiniLM need ~1.2 GB), set to suspend when idle and resume with memory intact, so idle cost is near zero and the model does not reload. Hardening: a `TRAILHEADRX_HTTPS=1` flag (set in the image, unset on a laptop) makes the sign-in cookie `Secure` and adds HSTS; every response gets a strict content-security policy (the site has no JavaScript, so `default-src 'self'` costs nothing), X-Frame-Options DENY, nosniff, and a referrer policy; the rate limiter reads Fly-Client-IP first, which Fly sets and a visitor cannot spoof. PyTorch is installed from the CPU wheel index so the image is a fraction of the default size. docs/DEPLOY.md is the runbook, including the GoDaddy records for trailheadrx.com and what things cost.

## 2026-09-20 — session 5, parts 2–4: daily refresh with email, nightly sweep, question-aware emphasis, form wording
**Refresh.** `trailheadrx refresh` fetches every policy URL and every maker program URL, fingerprints the content (visible text for HTML so nonces and timestamps do not cry wolf; bytes for PDF), saves and re-indexes a changed policy in place (`ingest.remove_document` + `ingest(documents=[doc])`), reports a changed program page without touching the hand-verified manifest, and stamps a checked-on date on every source. The footer shows "Plan documents last checked <date>"; the freshness guardrail counts that date as currency. Email through Resend (free tier; key and recipient are Fly secrets) only on a change or a *new* failure — a source still failing from yesterday is printed, not mailed. Scheduled by a GitHub Actions cron that runs the command inside the Fly machine over `fly ssh`, because a suspended machine cannot run its own timer and a separate scheduled machine cannot share the volume.

**Sweep.** `trailheadrx sweep` walks the menu (held plan × medicine × preset, no free text) through the same `compute()` the website uses — factored out of the job worker so both fill the same cache — and diffs each answer's summary, steps and months against the previous sweep's record. The cache is now disk-backed (`TRAILHEADRX_CACHE_DIR`, `/data/cache` on the server) so a redeploy keeps last night's answers. Budget: `precompute.daily_budget_usd` (default $3) stops the run; `--pairs N` limits it to the most-asked pairs from the audit trace; the nightly workflow uses 12.
